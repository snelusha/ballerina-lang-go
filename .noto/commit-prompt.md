# Commit Message Guidelines\n\n## Format\nSimple, direct prose starting with a verb. This style avoids conventional commit prefixes (like `feat:` or `fix:`) and parentheses-based scopes.\n\n## Style Rules\n- **Tense**: Imperative or present tense (e.g., \"Add\", \"Fix\", \"Refactor\").\n- **Capitalization**: Always capitalize the first letter of the message.\n- **Length**: Concise and focused, typically between 15 and 45 characters.\n- **Tone**: Technical and functional.\n\n## Commit Types\n- `Add`: Used for new files, features, or configurations.\n- `Fix`: Used for bug fixes, formatting corrections, or definition repairs.\n- `Refactor`: Used for restructuring code or definitions without changing behavior.\n- `WIP`: Used for work-in-progress changes, often followed by a colon and description.\n- `Cleanup`: Used for removing or tidying up migrated or legacy code.\n\n## Scope Usage\nNo formal scopes used. The context (e.g., specific nodes or packages) is included naturally within the description.\n\n## Description Patterns\nMessages follow a clear `[Action] [Subject]` pattern. The subject often uses technical abbreviations or specific class/interface names (e.g., \"st-node\", \"STNodes\", \"defn\").\n\n## Examples from History\n- Add type assertions for STNodes\n- WIP: transform func def\n- Refactor syntax tree defn\n- Fix formatting\n- Cleanup migrated code
